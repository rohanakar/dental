Web app

The browser app in apps/web. It loads intraoral scans, cleans them up off the main thread and shows them in a fast 3D viewer. Later it will host the crown design steps. This page covers how it is built, file by file.

In short
  • React for panels, a plain three.js Viewer class for 3D, and a Web Worker for all heavy geometry. React never touches three.js objects directly.
  • Import pipeline in the worker: parse, weld, clean up, normals and sha256, then a BVH (a spatial index for fast ray picking). The BVH is built once and shipped to the main thread without copying.
  • The viewer draws only when something changes. It orbits around the point under the cursor, and its standard dental views come from a PCA-estimated ViewFrame.
  • A 1M-triangle STL is processed and indexed in about 0.5 s in Node (measured on an Apple M3 Max).
  • Built on Day 1: import plus viewer. Planned: login and case upload (Day 2), design steps, undo and save (Days 2–5), AI panels (Day 6).

Layers

Each layer only calls the one below it. The rule that matters most: the engine never imports React, and the geometry code never touches the DOM. That keeps geometry testable in Node and lets the same code run in a worker or, later, in a headless pipeline runner.

Scan import pipeline

Importing a scan is the heaviest thing the app does today. All of it runs in the geometry worker, so the UI stays responsive while a 50 MB file is processed.

Deeper detail: ordering, the BVH index, transfers and colors Built · Day 1
  • Hash first. processScan hashes the original bytes with crypto.subtle before parsing, because later steps may reuse the buffer. The hash identifies the scan in MeshRef.sha256 and is checked by the backend on upload.
  • Weld before cleanup. specs/plan.md lists cleanup before weld, but the code welds first. Duplicate-face and connected-component detection both need shared vertex indices, which only exist after welding. The code's order is the correct one. Deviation
  • The BVH reorders the index. new MeshBVH(geometry, { indirect: false }) rearranges the triangle index buffer in place. The serialized BVH carries that reordered index, and the main thread uses it as the index (setIndex: false on deserialize). Face numbers therefore refer to the BVH order. They are never persisted: margins are stored as 3D points (see Data contracts).
  • Transfers. buildScanPayload collects positions, normals, colors, the BVH index, indirect buffer and every root buffer into a de-duplicated transfer list. A test asserts there are no duplicates (transferring the same buffer twice throws).
  • Colors. Scanner colors are sRGB bytes. three.js expects linear vertex colors, so the main thread converts them through a 256-entry lookup table into a Float32Array.
  • Latest wins. The key is the scan role. Dropping a second lower-jaw file while the first is still processing discards the first result (StaleResultError is swallowed by the controller). Removing an object calls cancelImport for the same reason.

The viewer

src/engine/Viewer.ts is a plain class around a WebGLRenderer. React creates one per viewport and talks to it only through its public methods.

Rendering on demand

A requestAnimationFrame loop runs continuously but only draws a frame when camera-controls reports movement or something called requestRender(): an object added or removed, an opacity change, a resize. A static scene costs almost nothing, which matters for laptop batteries during long design sessions. The device pixel ratio is capped at 2.

Camera and navigation

Cameras
Perspective (35° vertical field of view) and orthographic, swapped inside the same camera-controls instance.
Mouse
Left-drag rotate, right-drag pan, wheel zooms toward the cursor (dollyToCursor).
Cursor-centric orbit
A capture-phase pointerdown listener ray-casts under the cursor and calls setOrbitPoint before camera-controls sees the event. Rotation then pivots around the tooth you clicked on, not the scene centre.
Limits
Distance 2–1500 mm; smoothing 0.12 s (0.04 s while dragging).

Standard views and the ViewFrame

Dental views (occlusal, buccal, lingual, mesial, distal) are directions in a ViewFrame, not fixed world axes, because every scanner exports in its own coordinate system. Until the tooth frame exists (Day 2), estimateViewFrame guesses a whole-arch frame from the loaded jaws:

  • Up = the least-variance PCA axis (≈ the normal of the occlusal plane), oriented from the lower jaw's centroid toward the upper jaw's. With a single jaw, the average surface normal decides the sign.
  • Buccal = the second PCA axis, pointing toward the arch front. The front is the end with the smaller sideways spread (the incisors, not the two molar arms).
  • Mesial = up × buccal. For a whole arch this is just a side direction.
  • Occlusal view looks down from above for a lower jaw and from below when only an upper jaw is loaded.

Each view animates the camera to the new direction and frames the visible scans. Framing projects up to ~50k sampled vertices onto the camera axes and fits their extents with a 15% margin. That is much tighter than a bounding sphere for a flat, wide arch. The occlusal view gets a tiny buccal offset to avoid the gimbal singularity of looking straight down the up axis.

Perspective / orthographic toggle

Switching keeps what is on screen the same size. Going orthographic sets the frustum height to the visible height at the current target distance, then moves the camera back so the near plane never clips the model. Going back to perspective converts the zoomed orthographic height into a camera distance. In orthographic mode the wheel zooms instead of dollying.

Shading: matcaps and back faces

Surfaces use MeshMatcapMaterial with procedurally generated matcaps: a lit sphere baked into a texture, with key light, fill light, a specular highlight and a subtle rim. Shading is cheap and looks the same from every angle, which keeps margins and cusps readable. Presets:

PresetBase colour (sRGB)Used for
stone0.86, 0.82, 0.74Jaw scans (dental-stone look)
tooth0.96, 0.94, 0.88Restorations (kind: 'restoration', not used until the crown exists)
neutral0.95, 0.95, 0.95When "Show scan colors" is on, so the scanner colors dominate

Materials are double-sided. A shader patch (onBeforeCompile) tints back faces magenta (#b0496b) when gl_FrontFacing is false, so holes and the inside of open scans are obvious.

Transparency

Opacity below 1 switches a material to transparent with depth writes off. three.js then draws transparent objects after opaque ones, and draws double-sided transparent materials in two passes (back faces, then front faces). While an object is transparent its back-face tint is turned off, so the far side reads as surface rather than as a hole.

Picking and screenshots

raycast(clientX, clientY) uses three-mesh-bvh's accelerated raycast with firstHitOnly over the visible objects. It returns the object id, point, normal, distance and the BVH-order face index. screenshot() renders a frame and reads it back immediately with toDataURL, so the renderer does not need preserveDrawingBuffer (which would slow every frame).

State and the React↔engine boundary

There are two kinds of state and they live in different places:

Serializable UI state → useSceneStoreNames, roles, import phase, visibility, opacity, stats, warnings, projection. React components subscribe with selectors.
Heavy, non-serializable state → sceneControllerBufferGeometry objects with their BVHs, and the Viewer reference. Keeping them out of the store avoids accidental copies and re-renders.

UI events call controller methods (setOpacity, setView, importFile…). The controller updates the store and the viewer, so the two never drift. attachViewer re-adds already-loaded geometry, which keeps hot module reload and remounts working.

DecisionAn imperative engine instead of react-three-fiber: render-on-demand, cursor-centric orbit and, later, sculpting need tight control over the render loop and input order. See the Decision log.

Base path and URLs

The app runs at the root of https://dental.cognifuze.com, but it can also be mounted under a sub-path such as /dental/. Nothing hardcodes absolute URLs:

  • vite.config.ts reads VITE_BASE_PATH (Docker build arg or .env) and normalizes it to a leading and trailing slash (dental → /dental/, empty → /).
  • apiUrl('cases') → ${BASE_URL}api/cases; assetUrl() does the same for static files.
  • The worker URL is resolved with new URL(…, import.meta.url), so it follows the base too.
  • The dev server (port 5173) and preview server (4173) proxy ${base}api to http://localhost:3000 and rewrite it to /api, the API's internal prefix.

See Deployment & operations for how the proxy strips the prefix in production.

Performance

The automated perf test (src/workers/scanPayload.test.ts, "1M-triangle import performance") imports a synthetic 1,000,000-triangle binary STL (50 MB) in Node and builds the BVH. One run during this documentation pass, on an Apple M3 Max:

StageTimeNotes
Parse16 msBinary STL into a triangle soup
Weld59 ms3M soup vertices → ~500k vertices
Clean up65 msDegenerate, duplicate, components
Normals27 ms
processScan total195 msIncludes sha256 and format detection
BVH build + serialize278 ms
Total473 msSoft assertion: < 5 s

Timings vary by a few tens of milliseconds between runs (the Day 1 builder recorded 467 ms total). In the browser, the 1M-triangle demo lower arch plus the 300k-triangle upper arch were ready about 0.8–1 s after clicking, observed manually in headless Chrome during the Day 1 check (not an automated test). The plan's targets are a 1M-triangle arch loading in under 3 s and orbiting at 60 fps on a mid-range laptop; the fps target has not been measured yet.

Production bundle: main chunk 892 kB (241 kB gzipped), mostly three.js; worker chunk 186 kB. The chunk-size warning limit is raised to 1200 kB on purpose.

Known limits

  • One scan per role. The role doubles as the object id, so a second lower-jaw file replaces the first. Roles are upper, lower and preop.
  • The view frame is a guess. The PCA heuristics assume a full arch; quadrant scans or unusual exports may get a wrong "up" or "front". The Day 2 tooth frame replaces it for design work.
  • Units are only checked, not fixed. Scans larger than 200 mm or smaller than 5 mm across get a warning; nothing is rescaled.
  • No undo, no persistence, no login yet. Closing the tab loses the session. better-auth and fflate are installed but unused until Days 2 and 5.
  • Face indices are not stable. They refer to the BVH-reordered index and must never be stored.
  • No WebGL context-loss handling in Viewer.ts yet.
  • Color conversion on the main thread. Turning sRGB colors into a Float32Array costs one allocation per import on the main thread. That is fine at current sizes.
