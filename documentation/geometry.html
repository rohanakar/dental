Geometry pipeline

How a pair of intraoral scans becomes a single posterior crown that seats on the prepared tooth: every algorithm, in pipeline order, with its status. Each step has a plain-language explanation first; the math is in the expandable blocks.

In short
  • Built: scan import (parse, weld, clean up, normals, unit check) and PCA for orientation.
  • Planned (Days 2–5): tooth frame, live-wire margin, insertion axis, inner surface (intaglio), crown fit from a template library, thickness and occlusion adaptation, stitching, validation and colour maps.
  • Every step is deterministic and runs in a Web Worker. AI proposers will plug in behind the same inputs and outputs later (see AI assist).
  • Two first-draft ideas were rejected after review: a grid-based dilation for the cement gap (it nearly erases the gap on steep walls), and milling-tool compensation in CAD (it makes the crown loose).
  • The output is watertight by construction (a strip joins the outer and inner rims) and then checked for holes, flipped faces and self-intersections.

End-to-end data flow

One crown, from scans to the file a milling machine or printer receives. Each box names the step's output; the output types already exist as zod schemas in packages/shared/src/design.ts, even where the algorithm is not built yet.

Conventions

Units
Millimetres everywhere. Scans are assumed to be in mm; the importer only warns if the size looks wrong.
Meshes
IndexedMesh: Float32Array positions, Uint32Array indices, optional Uint8Array colors and Float32Array normals (apps/web/src/geometry/mesh.ts). Plain typed arrays, so they move between threads without copying.
Frames
Scans keep their native scanner frame (MeshRef.frame = 'scan'). Crown deltas live in the tooth-local frame so they survive pose changes.
Stable references
Face indices are not stable: the BVH build reorders them and future cuts would too. Anything persisted (margins, contacts) is stored as 3D points with at most an optional faceHint.
Where code runs
Heavy steps in the geometry worker; picking, gizmo and (later) sculpt on the main thread, where the crown is only tens of thousands of vertices.

Built today: scan import

Implemented in apps/web/src/geometry/ and orchestrated by processScan(). Order: hash → parse → weld → clean up → normals → stats and warnings. The BVH is built afterwards in the worker (see Web app).

Parsing STL and PLY Built · Day 1

Input
File bytes + file name
Output
STL: a triangle soup (9 floats per triangle). PLY: an indexed mesh with optional colors.

STL repeats every shared corner for each triangle and has no units or colors. PLY is indexed and often carries the scanner's colors, which help tell gum from tooth.

Deeper detail: format detection and parser coverage
  • Binary vs ASCII STL is decided by size: binary files are exactly 80 + 4 + 50 × faces bytes. The leading text "solid" is not trusted, because some binary exporters write it into the header. Truncated binary files are read up to the last complete face. Stored facet normals are ignored and recomputed.
  • ASCII STL is read with a single regular expression over vertex x y z lines.
  • PLY: ASCII, binary little-endian and binary big-endian; all scalar types (char…double and their sized aliases). Float colors are scaled to 0–255. Faces use vertex_indices or vertex_index lists; polygons are fan-triangulated; unknown elements and extra properties are skipped. Faces referencing missing vertices are rejected.

Welding Built · Day 1

Turns the STL soup into an indexed mesh by merging corners that are the same point. Without this, there is no connectivity: no curvature, no paths along the surface, no smoothing.

Deeper detail: exact float-bit welding

Two vertices merge only if their three float32 bit patterns are identical, with -0 treated as +0. STL exporters write shared corners bit-identically, so no tolerance is needed, and an exact match can never merge two genuinely different points (a tolerance can, on fine scans).

Implementation (weld.ts): an open-addressing hash table over the raw Uint32 bits, with a spatial-hash style mix (x·73856093 ⊕ y·19349663 ⊕ z·83492791) and linear probing. No string keys, so 3M soup vertices weld in tens of milliseconds. The remap array becomes the index buffer directly, because soup vertex k belongs to triangle ⌊k/3⌋. PLY files go through the same weld (weldIndexed) to merge duplicated vertices, keeping the first vertex's color.

Cleanup Built · Day 1

Removes geometry that breaks later algorithms: zero-area slivers, triangles listed twice, and loose fragments of scan debris (tongue, cheek, floating specks).

Deeper detail: thresholds and methods
  • Degenerate faces: repeated vertex indices, or |(b−a) × (c−a)| ≤ 2 × 10⁻¹⁰ mm² (twice the minimum area). The comparison also rejects NaN.
  • Duplicate faces: the three indices are sorted and hashed, so the same triangle with either winding counts as a duplicate. The first occurrence is kept.
  • Small components: union-find over faces sharing vertices. Components with fewer than 1% of the largest component's faces are dropped (smallComponentRatio = 0.01).
  • Unused vertices are compacted away at the end; the importer reports what it removed as user-visible warnings.

Normals, unit check and hashing Built · Day 1

  • Normals: each face adds its unnormalized cross product (length = twice its area) to its three corners, then each vertex normal is normalized. Big faces count more, small slivers barely matter.
  • Unit check: an arch is roughly 10–80 mm across. If the largest bounding-box extent is over 200 mm or under 5 mm, the importer warns that the file may not be in millimetres. It does not rescale.
  • Hash: sha256 of the original file bytes, used as the scan's content address (MeshRef.sha256) and verified by the backend on upload.

PCA orientation Built · Day 1

Principal component analysis finds the three directions along which the scan's points spread most and least. For a dental arch, the least-spread direction is close to the normal of the biting (occlusal) plane. Today this drives the viewer's standard views; on Day 2 it becomes the first step of the tooth frame.

Deeper detail: computation

principalAxes() subsamples to at most 200,000 points, computes the centroid and the 3×3 covariance matrix, and diagonalizes it with a cyclic Jacobi eigen-solver (symmetricEigen3, up to 50 sweeps, stops when off-diagonal mass < 10⁻¹⁴). Axes are returned sorted by decreasing variance. A test checks that the least-variance axis of the synthetic arch is within ~18° of +z (|z| > 0.95). The whole-arch heuristics built on top (up from the lower-to-upper centroid direction, front = the narrow end of the arch) are described on the Web app page.

Planned algorithms

None of the following is implemented yet. The descriptions follow specs/plan.md as revised after the design review; exact constants will be tuned on the golden cases. Where a formula is given as a candidate, it is a starting point rather than a decision.

Tooth frame Planned · Day 2

Input
Prep jaw mesh, antagonist (opposing jaw) mesh, FDI tooth number, margin centroid when available
Output
ToothFrame: origin, occlusal, mesial, buccal, optional mesialContact / distalContact, source

A small coordinate system attached to the tooth being restored: which way is "up" toward the opposing teeth, which way is toward the front of the mouth along the arch (mesial), and which way is toward the cheek (buccal). Fit, scaling, adaptation, the gizmo and the AI agent's "move 0.2 mm mesial" all depend on it, which is why it became an explicit step after the review.

Deeper detail: directions and neighbour contacts
  • Occlusal: least-spread PCA axis of the prep jaw, flipped if needed so it points toward the antagonist's centroid.
  • Mesial–distal: for a quadrant scan, the long PCA axis. For a full arch, the tangent of a parabola fitted to the arch in the occlusal plane, evaluated at the tooth's position. The sign points toward the midline (from the FDI quadrant).
  • Buccal: completes an orthonormal, right-handed frame and points away from the inside of the arch.
  • Neighbour contacts: cast rays along ±mesial from the margin centroid, ignoring hits on the prep region and a gingival ring around it. The first hits on each side are the contact points. The user can override them with two clicks; source records auto or manual.

Margin line: live-wire Planned · Day 2

Input
Prep jaw mesh with BVH, user clicks (anchors)
Output
MarginLine: ordered anchors (≥ 3), dense resampled closed points, source; plus the prep region (faces inside the margin)

The margin is where the crown will end on the prepared tooth, and it is the most precision-critical line in the design. The tool works like a magnetic lasso: after each click, the path to the cursor follows the sharp ridge of the preparation and updates live as the mouse moves. Clicks pin anchors; closing the loop finishes the line. Anchors can be dragged later.

Deeper detail: path cost, signed curvature and the prep region

Path search. A bounded single-source Dijkstra on the mesh edge graph runs from the last anchor each time one is placed, so the path to any cursor position is a lookup. The bound keeps it interactive on 1M-triangle scans.

Edge cost. cost(e) = |e| · f(κ), where κ is the signed curvature across the edge, estimated over about 0.3 mm on smoothed normals, and f is small on convex ridges and large elsewhere. A candidate estimate for edge (i, j):

κ_ij = ((n_i − n_j) · (p_i − p_j)) / |p_i − p_j|²
// > 0 on convex surfaces (normals diverge), < 0 on concave ones.
// On a sphere of radius r with outward normals this gives exactly 1/r.

Why signed. Unsigned measures (dihedral angle) are just as high in concave creases: the gingival sulcus next to the prep and the floor of a chamfer. On noisy intraoral scans the path would snap into those. Only convex ridges are cheap.

Result. The anchors' paths form a closed loop of mesh edges. A flood fill from inside that loop gives the prep region, widened by 1–2 rings of faces so later steps see the margin's surroundings. The loop is resampled to even spacing, smoothed, and re-projected onto the surface with BVH closest-point queries to give points. Only 3D points (plus an optional face hint) are stored.

Insertion axis and undercut map Planned · Day 2

Input
Prep region, margin, tooth frame
Output
InsertionAxis (direction, source), a per-vertex undercut value, and a warning if the margin itself is in undercut

The direction along which the crown slides onto the tooth. Any part of the preparation that bulges out beyond what is visible from that direction (an undercut) would block the crown, so it gets filled in ("blocked out") on the inside of the crown. The best axis is the one needing the least blockout.

Deeper detail: cone search
  • Candidates: directions within a cone of about 25° around the occlusal direction.
  • For each candidate a, measure blockout. A simple proxy is Σ area(f) · max(0, −n_f · a) over prep faces. The exact measure can be the volume added by the ray-cast envelope used for the intaglio.
  • Pick the minimum. The mean surface normal is not used, because it is biased by uneven wall areas.
  • Undercut map: per-vertex dot(normal, axis); negative values face away from the insertion direction.
  • Warn if any margin point is in undercut, i.e. not visible along +a: the crown edge could not reach it.
  • The user can also set the axis from the current view direction.

Intaglio (inner crown surface) Planned · Day 3

Input
Prep region, margin points, insertion axis, cementGapMm, extraSpacerMm, distanceToMarginMm
Output
An open mesh whose boundary is exactly the resampled margin points

The inside of the crown that sits on the prepared tooth. It must be a copy of the prep, pushed out by a thin, even gap for cement, with undercuts filled in, so the crown slides on along the insertion axis and seats fully. Getting this right is the most likely place for the week to slip.

Deeper detail: gap profile, envelope and radial meshing

1. Gap profile. The offset depends on d, the distance from the margin. The gap is 0 at the margin (the crown edge must fit tightly) and ramps up to the cement gap over 0.1–0.2 mm. Beyond distanceToMarginMm the extra spacer is added. A candidate shape:

gap(d) = cementGap · ramp(d / w)  +  extraSpacer · ramp((d − D) / w)
ramp(t) = clamp(t, 0, 1) smoothed (e.g. smoothstep)
w ≈ 0.1–0.2 mm,  D = distanceToMarginMm

2. Offset. Each prep vertex moves along its smoothed normal: p′ = p + gap(d) · n̂. Because the offset is along the true surface normal, steep axial walls get the full gap.

3. Envelope (blockout). Cast rays along −axis onto the offset surface (using its BVH) and keep the first hit. Anything hidden underneath, the undercuts, is replaced by the "shadow" seen from above, so the result has no undercuts by construction.

4. Radial-profile meshing. For each of the N resampled margin points, sample a profile toward the prep centre (in the plane perpendicular to the axis), ray-casting the height at each sample. Resample each profile by 3D arc length to M points, so steep walls get as many samples as flat areas. Connect neighbouring profiles with quads (two triangles each) and close the centre with a fan. The boundary is exactly the margin points, so stitching later is a simple index match, and no constrained-Delaunay library is needed.

Assumption. The margin, projected along the axis, must be star-shaped around the centre: every ray from the centre crosses it once. That is normal for posterior preps. The step checks this and warns instead of producing a folded mesh.

Rejected: heightfield dilation for the cement gap The first draft rasterized the prep onto a 0.05 mm grid along the insertion axis and applied a spherical dilation of radius equal to the cement gap. A cement gap of 0.02–0.04 mm is smaller than one grid cell, so the dilation degenerates into a plain vertical shift by the gap. On an axial wall tapered about 5° from the axis, a vertical shift moves the surface only gap × sin 5° along its normal: 0.04 × 0.087 ≈ 0.003 mm instead of 0.04 mm. Crowns would bind on the walls and not seat. The review replaced it with the normal offset above. See the Decision log.

Unmillable map and tool radius Planned · Day 4

Input
Intaglio, insertion axis, toolRadiusMm (R)
Output
A colour map marking regions a ball-end tool of radius R cannot reach

A milling bur has a rounded tip, so it cannot cut a concave corner inside the crown that is tighter than its own radius. Those spots correspond to sharp convex edges on the prep. The app shows them so the technician or dentist can decide (round the prep, or accept CAM relief); it does not change the surface.

Deeper detail: morphological opening, and why no compensation in CAD

Map. Build a heightfield of the intaglio along the insertion axis and apply a morphological opening with a ball of radius R (erosion, then dilation). Where the opened surface differs from the original, the tool cannot follow the surface.

Why not compensate. The first draft dilated the whole intaglio by R (0.3–0.5 mm). That overcuts every surface by the tool radius and produces a loose crown. Real compensation is only needed locally, as small relief cavities at sharp convex prep edges, and the CAM software already does this with its knowledge of the actual tools. So compensation is left to CAM; toolRadiusMm drives only this map.

Stretch goal. Optional relief domes: a ball of radius R centred at p − R·n at sharp convex edges sharper than R.

Template library Planned · annotation Days 0–3

Crowns start from library teeth: 8 hand-annotated templates (first premolar, second premolar, first molar, second molar, for the upper and lower jaws). The opposite side of the mouth uses mirrored copies. Each template is an open outer shell: only the visible tooth surface, ending in a rim at the gum line (the cervical loop).

Deeper detail: template contents and mirroring
  • Per template: the shell mesh; the cervical loop pre-resampled offline to a fixed N points; metadata (FDI number, local axes, cusp tips).
  • Mirroring: reflect across the sagittal plane of the template frame and flip the triangle winding (swap two indices per face), otherwise normals point inward.
  • Built by tools/library-builder/ (planned). The review cut this from "extract templates from all 100 cases" to 8 annotated templates; separating the outer surface from the intaglio and building canonical frames was several hidden days of work.
  • In the document, a template crown is { kind: 'template', templateId, pose, deltas? }; ML-generated crowns will use { kind: 'mesh', mesh } instead.

Crown fit Planned · rigid Day 3, RBF Day 4

Input
Template, tooth frame, neighbour contacts, margin points, antagonist, marginThicknessMm
Output
Template pose plus a deformation that puts the template's rim on the margin

The library tooth is placed over the prep, scaled to the space available, and its rim is pulled down onto the margin line while the chewing surface keeps its anatomy. The Day 3 walking skeleton uses rigid placement only; the deformation arrives on Day 4.

Deeper detail: placement, loop matching and RBF deformation
  1. Place at the margin centroid, aligned with the tooth frame.
  2. Scale anisotropically: mesial–distal from the gap between the neighbour contacts; bucco-lingual from the margin's extent; height from the space to the antagonist.
  3. Match the loops. Offset the margin outward by the margin thickness and resample it to the same N as the template rim. Pair points by normalized arc length starting from the most mesial point, with both loops in the same winding. Pairing by angle around the axis can silently twist the joining strip.
  4. Deform with radial basis functions. Known displacements at the N rim points (target − current) and zero displacement at anchor points on the occlusal third. Solve the RBF interpolation (a few hundred centres, a small dense solve) and apply it to every shell vertex. RBF instead of Laplacian deformation because JavaScript has no practical sparse solver.
  5. Re-solve on every pose change. The rim band stays locked during transforms and sculpting.

Thickness constraint Planned · Day 4

A crown that is too thin cracks. After fitting, adapting or sculpting, any part of the outer surface that is too close to the intaglio is pushed outward. This is enforced, not just reported, because "edge count is right" checks cannot see an outer surface dipping inside the inner one.

Deeper detail: the thickness profile

For each outer vertex, t(v) = distance to the intaglio (BVH closest point). The required thickness rises from marginThicknessMm at the margin to minThicknessMm within about 1 mm. If t(v) is below the requirement, move v outward along its normal by the difference. Runs after every fit, adapt and sculpt operation.

Adapt to antagonist and neighbours Planned · Day 5

Makes the crown just touch, or clear by a target gap, the opposing teeth when biting (occlusalClearanceMm) and the neighbouring teeth at the sides (proximalContactMm). The AI agent's adapt_occlusion and set_contact tools call this step.

Deeper detail: displacement-field smoothing and conflict reporting
  • Antagonist: measure clearance along the axis from each occlusal-facing vertex to the antagonist (BVH ray cast). Where clearance differs from the target, compute a displacement along the axis.
  • Neighbours: same idea along the mesial–distal direction, limited to proximal-facing vertices in the upper two thirds of the crown. Otherwise the gum-side shape (emergence profile) would be ruined.
  • Smooth the displacements, not the positions. Laplacian smoothing of the displacement field spreads the change over the region while keeping cusps and grooves sharp. Smoothing positions would erode them. Repeat 2–3 iterations.
  • Conflicts: if reaching the clearance would violate the minimum thickness, stop and report "insufficient reduction" (the tooth needs more preparation) instead of looping or producing a thin crown.

Stitching and validation Planned · stitch Day 3, full checks Day 5

The outer shell and the intaglio are joined into one closed solid, then checked before anything is exported.

Deeper detail: watertight by construction, then verified

Stitch. Both rims have the same N points in matching order, so a triangle strip connects point i on the outer rim to point i on the intaglio rim. No boolean operation is needed.

Validate:

  • Closed manifold: every edge is shared by exactly two faces.
  • Consistent orientation: each directed edge appears once.
  • Outward normals: signed volume V = ⅙ Σ a · (b × c) > 0 over all faces.
  • No triangle–triangle intersections, found with a BVH self-query that skips adjacent faces. This is what catches the outer surface crossing the intaglio.

manifold-3d (WASM) is kept only as a boolean repair fallback; it does not detect self-intersections, so it is not the validator.

Export. Binary STL (the writer already exists in stl.ts) plus a JSON sidecar similar to exocad's .constructionInfo: tooth number, margin, insertion axis, material.

Colour maps Planned · material Day 3, maps Day 4

Heatmaps painted on the surfaces: undercut, distance to the antagonist, proximal contacts, crown thickness, unmillable regions. Technicians look at them constantly while adjusting a crown.

Deeper detail: rendering and update cost

The worker computes one Float32Array scalar per vertex (BVH distance queries); a shader maps it through a 1D lookup texture with a uniform value range, and React shows the legend. During adaptation only changed vertices are recomputed. Plan target: a colour-map update under 100 ms during adapt.

Lasso cut Planned · on the cut list

Deleting scan debris by drawing a lasso. Stored as a face-mask bitset over the BVH-ordered faces and only compacted at export, so indices do not shift mid-session. This is one of the first features to drop if the week runs short; automatic small-component removal already handles most debris.

Risks and open questions

  • Intaglio correctness and fit without intersections are the two most likely slips in the schedule.
  • Curvature tuning: the live-wire cost function and the 0.3 mm smoothing radius need tuning on real intraoral scans; synthetic arches are too clean.
  • Star-shaped margins: true for typical posterior preps; unusual preps will get a warning and a manual fallback.
  • Quadrant vs full-arch scans: the mesial–distal estimate uses different methods for each; both need golden cases to validate.
  • No real scans yet: everything built so far was tested on synthetic arches. The 3–5 de-identified golden cases are the main dependency for Day 2.
