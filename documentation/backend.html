Backend API

The API in apps/api is a small Node 22 + Hono service. It handles sign-in and labs (organizations), stores scans and design versions, and proxies LLM calls. Every external system sits behind a port, so the backend can leave this VM by changing configuration rather than code.

In short
  • Ports and adapters. Domain code (src/domain) never imports infrastructure. Postgres, file storage, auth, LLM providers, jobs and rate limiting are adapters chosen by env vars at startup in src/main.ts. Built · Day 1
  • Every query is scoped to the caller's organization (lab). A user from another lab gets 404, never someone else's data. Each new user gets a personal lab automatically.
  • Scan uploads are streamed, not buffered. The size limit and the sha256 integrity check (of the decompressed bytes for gzip) are both enforced while streaming. On any failure the stored blob is deleted.
  • Design saves use optimistic concurrency. If someone else saved first, the API answers 409.
  • The LLM proxy holds the keys and picks provider and model. The browser runs the agent loop and cannot choose a model. Responses are non-streaming for now. SSE streaming planned

Ports and adapters

The API has three layers. HTTP routes validate input and call domain services. Domain services enforce the rules (org scoping, integrity, concurrency) and talk only to ports, which are TypeScript interfaces in src/ports. Adapters in src/adapters implement the ports and are wired together once in src/main.ts, and again in the tests with test doubles or containers via createApp(deps).

Request lifecycle

Every request passes through the same middleware chain in src/http/app.ts:

  1. Request id. An incoming X-Request-Id header (first 64 characters) is reused, otherwise a UUID is generated. It is echoed in the response header and attached to every log line for that request.
  2. Unauthenticated routes. GET /healthz and GET /api/healthz ping the database. /api/auth/* (GET and POST) is handed to Better Auth unchanged.
  3. Auth guard. Everything else under /api/* calls AuthPort.resolve(headers). No session gives 401 unauthorized. A signed-in user with no organization gives 403 no_organization. Otherwise the context {userId, orgId, role} is stored on the request and added to the logger.
  4. Validation. JSON bodies go through bodyLimit(MAX_JSON_BYTES) (default 10 MB) and the zod schemas from @dcad/shared (readJson, readQuery). A failure gives 400 validation_error with a per-field issue list.
  5. Org scoping. Every repository method takes orgId and filters on it. A case or file from another org is indistinguishable from a missing one (404).
  6. Errors. Domain code throws DomainError(code, message, details?). handleError maps it to an HTTP status and the shared ApiError shape { error: { code, message, details? } }. Unknown routes return 404 not_found in the same shape, and unexpected exceptions return 500 internal_error (logged with the request id).

Auth and organizations

Authentication is Better Auth, a TypeScript library rather than a hosted service. It runs inside the API with email/password sign-in (minimum password length 10) and its organization plugin. Its tables (user, session, account, verification, organization, member, invitation) live in our own Postgres and are generated into the same Drizzle migration as the app tables (pnpm --filter @dcad/api auth:schema).

  • A personal lab on sign-up. A user.create.after hook creates an organization named <name>'s lab (slug lab-<userId>) with the user as owner, so every row is org-scoped from the first case.
  • Active organization. A session.create.before hook sets the session's activeOrganizationId to the user's first membership. resolve() re-checks that the user is still a member of the active org, which covers a stale session after removal from an org. If not, it falls back to the first membership, or returns "no organization" (403).
  • Cookies. Session cookies are scoped to Path=BASE_PATH (or / at the root). They are marked Secure when NODE_ENV=production and PUBLIC_URL is https. Trusted origins are the PUBLIC_URL origin plus TRUSTED_ORIGINS (e.g. the Vite dev server).
  • Rate limiting of auth routes uses Better Auth's built-in limiter. Its default turns it on only in production mode, which Compose sets (NODE_ENV=production).
Deeper detail: sub-paths and the Better Auth baseURL gotcha

The app can be mounted at a domain root (primary: https://dental.cognifuze.com) or under a sub-path (e.g. https://example.com/dental). Caddy strips the sub-path, so requests reach the API as /api/auth/....

Better Auth ignores its basePath option when baseURL already contains a path, and routes on baseURL's pathname instead. The adapter therefore:

  1. passes baseURL = PUBLIC_URL + "/api/auth", so every link Better Auth generates is a correct public URL, and
  2. in handler(), re-adds the stripped BASE_PATH to the request URL before handing it to Better Auth (body streamed with duplex: 'half').

The integration test "accepts proxy-stripped auth requests and scopes cookies to the sub-path" covers this.

Swapping auth laterMoving to an external OIDC provider (Keycloak, Auth0, Cognito, OCI Identity Domains) means writing one new AuthPort adapter that resolves {userId, orgId, role} from a token. Routes and domain code do not change.

Scan upload and download

Intraoral scans are large: tens of MB as STL, and the limit is 200 MB by default. The browser gzips the scan, computes the sha256 of the uncompressed bytes, and posts the raw body. The API never holds the whole file in memory.

  • Download (GET /api/files/:id) streams the stored bytes with Content-Type, Content-Length, an RFC 6266 Content-Disposition with a UTF-8 file name, ETag and X-Content-Sha256 (both the sha256), and Cache-Control: private, max-age=31536000, immutable (files are content-addressed). When stored gzipped, it adds Content-Encoding: gzip, so browsers decompress transparently.
  • Content type is taken from the request only if it matches a safe type/subtype pattern, else application/octet-stream.
  • Why through the API and not presigned URLs? It keeps every storage backend interchangeable (fs has no presigned URLs) and lets the API verify integrity. Presigned multipart uploads are a later scale optimization. Post-MVP
MeasuredIn the backend builder's local Compose run (Apple Silicon Docker, not the VM), a 150 MB upload took about 1.1 s while the API process stayed at about 112 MiB, and a 210 MB upload got 413. In the Day 1 smoke test, the 50 MB synthetic 1M-triangle STL gzipped to about 23 MB, and the download's sha256 matched the original.

Design versions and optimistic concurrency

A case's design is saved as an immutable DesignDocument snapshot in design_versions. cases.current_version counts saved versions (0 = none yet).

  • The client sends parentVersion = the version it started from. In one transaction, the repository runs a compare-and-swap: UPDATE cases SET current_version = current_version + 1 WHERE org_id = ? AND id = ? AND current_version = parentVersion, then inserts the new version row with the bumped number.
  • If no row was updated and the case exists, the save fails with 409 conflict and details.currentVersion, so the client can reload and retry. If the case does not exist in the org, it gets 404.
  • doc.caseId must match the URL case (400 otherwise). author is user, agent or proposer, so AI-made versions are distinguishable.

LLM proxy

The agent tool loop runs in the browser, where the geometry and metrics live. The API is a thin, authenticated proxy so that keys never reach the browser and the server controls which model is used. See AI assist for the loop itself.

  • Provider selection happens once at startup (src/config.ts), separately for agent and rx-intake:
    1. An explicit LLM_AGENT_PROVIDER / LLM_RX_PROVIDER wins.
    2. Otherwise Anthropic if ANTHROPIC_API_KEY is set, else OpenAI if OPENAI_API_KEY is set, else the mock.
    3. A provider without its key falls back to the mock with a warning.
  • Models: defaults are claude-sonnet-5 (Anthropic), gpt-5 (OpenAI) and mock-1. LLM_RX_MODEL falls back to LLM_AGENT_MODEL. A configured model that doesn't match the chosen provider (a claude-* name on OpenAI or vice versa) is ignored with a warning. If LLM_MODEL_ALLOWLIST is set, startup fails when a configured model is not on it. The chosen provider and model are logged at startup; keys never are.
  • Wire format: the shared, provider-agnostic LlmRequest/LlmResponse with text, image, tool_call and tool_result parts. The Anthropic adapter maps these to Messages API blocks (tool_use, tool_result, base64 images) and drops thinking or server-tool blocks from responses. The OpenAI adapter maps them to Chat Completions: tool results become tool messages and images become data URLs.
  • OpenAI strict mode: tool schemas from agentToolDefs() are normalized by toOpenAiStrictSchema: every object gets additionalProperties: false, every property becomes required with originally-optional ones made nullable, and unsupported keywords are dropped. Nulls in responses are stripped again so the browser's zod validation sees "absent".
  • Rate limit: MemoryRateLimiter, a fixed 60-second window per user, default 30 requests (LLM_RATE_LIMIT_PER_MIN). Over the limit returns 429 with Retry-After. It is in memory, so it is valid for one API instance only.
  • Usage logging: every successful call inserts an llm_usage row (org, user, purpose, provider, model, input and output tokens). Provider failures become 502 upstream_error.
  • Mock provider: deterministic and offline. It echoes mock: <text>. If the last user text is /tool <name> {json} and that tool was offered, it returns a tool call, which lets the agent loop be tested without keys.
  • Limits: up to 200 messages and 64 tools per request, maxTokens 1–16,000 (default 2048), system prompt up to 20,000 characters.
Not built yetResponses come back in one piece. Server-sent-event streaming is planned Planned. Payloads must carry no patient identifiers: CaseSetup.patientRef is pseudonymous by design, but the proxy does not scrub content.

Data model

One Postgres database holds both the app tables (src/adapters/db/schema.ts) and the Better Auth tables (auth-schema.ts). Every app table carries org_id (FK to organization, cascade delete), and repositories always filter on it. The single migration is apps/api/drizzle/0000_init.sql.

Deeper detail: indexes and column notes
  • cases_org_updated_idx (org_id, updated_at) serves the case list.
  • case_files_org_case_idx (org_id, case_id) and case_files_sha_idx (sha256), the latter ready for de-duplication and training-bundle lookups.
  • proposal_events_org_case_idx (org_id, case_id) and proposal_events_step_idx (step, proposer_id), for flywheel analysis per proposer.
  • llm_usage_org_created_idx (org_id, created_at), for usage reports.
  • cases.teeth is denormalized from setup.teeth[].fdi for listing. design_versions.doc and proposal_events.event store the full shared-schema JSON.
  • case_files.blob_key is orgs/<org>/cases/<case>/<fileId> and is never returned to clients.
  • Schema changes: edit schema.ts, then pnpm --filter @dcad/api db:generate, and commit the new SQL. Migrations run on start when MIGRATE_ON_START=true.

Configuration reference

The API reads environment variables, validated by zod in src/config.ts. Startup fails with a list of every invalid key. Empty values count as unset, so OPENAI_API_KEY= in .env is fine. In development the API reads the repo-root .env (--env-file-if-exists=../../.env). In Compose the api container loads the same file via env_file. Compose-only keys (POSTGRES_*, VITE_BASE_PATH) are covered in Deployment & operations.
