Guide For: developers and testers trying the app

Demo mode & sample data

What happens when you click Load demo scans, why there is no demo file anywhere in the repo, and how to try the app with your own scans.

In short
  • There is no demo file. The demo jaws are generated by code in the browser each time you click the button. The math lives in apps/web/src/geometry/synthetic.ts.
  • The generated jaws go through exactly the same import pipeline as a real scan, so the demo exercises real code.
  • Need the demo as files? pnpm --filter @dcad/web fixtures writes STL/PLY copies to data/synthetic/.
  • Your own scans: drag STL/PLY files onto the left panel. Files whose names contain "upper"/"lower" get that role automatically. Everything stays in your browser; nothing is uploaded yet.
  • Keep real scans under data/, which git ignores, and de-identify them first (file names and file headers).

What the demo button does

The button appears in two places: the left panel (apps/web/src/ui/ScanImport.tsx) and the empty viewport (apps/web/src/ui/Viewport.tsx). Both call the same function.

Deeper detail: how syntheticArch() builds a jaw
  1. It lays a grid of along × across points over a U-shaped band (an ellipse arc of radii 24 and 26 mm, 12 mm wide). The number of triangles is 2 × along × across.
  2. For each grid point it works out which tooth it's on (by walking the arc with real mesio-distal widths: 8.5, 6.5, 7, 7, 7, 11, 10 mm from the midline back) and where on that tooth (a local mesial and buccal coordinate).
  3. It raises the point by a "superellipse dome" height for that tooth. Premolars and molars subtract cosine ripples to form cusps. For tooth 36, it uses a stump profile instead: flat top, steep walls, a shoulder near the edge.
  4. Upper jaw: the same, mirrored and lifted so the cusps nearly touch.

The same generator feeds unit tests (e.g. "imports a synthetic arch STL without warnings", "finds the occlusal plane"), so tests and demo always agree.

Getting the demo as files

To test drag-and-drop, file parsing or your own tools against the demo shapes, write them to disk:

pnpm --filter @dcad/web fixtures
# → data/synthetic/lower.stl          50 MB   (1,000,000 triangles, binary STL)
# → data/synthetic/upper.stl          15 MB   (300,000 triangles)
# → data/synthetic/lower-colored.ply  6.2 MB  (300,000 triangles + vertex colours)
# → data/synthetic/upper-colored.ply  6.2 MB  (300,000 triangles + vertex colours)

# smaller or bigger lower jaw:
node --experimental-strip-types tools/fixtures/generate.mts --triangles 200000

The script is tools/fixtures/generate.mts. It imports the web app's own generator and writers, so there's no duplicate code. Note the size difference: STL stores every triangle's three corners separately (50 bytes per triangle), while PLY stores each corner once and refers to it by number. For the same 300,000 triangles that's 15 MB as STL vs 6.2 MB as PLY, even though the PLY also carries colours.

Using your own scans

  1. Run the app: pnpm dev:web and open http://localhost:5173.
  2. Drag one or more .stl / .ply files onto the drop zone in the left panel, or use the file picker.
  3. Each file gets a role (upper, lower, pre-op). The app guesses it from the file name; files it can't place take the role selected in the panel, then the other jaw.

Rules live in apps/web/src/ui/files.ts (roleFromFileName, assignRoles) and are unit-tested. Dropping a new file for a role replaces the old one, and a slower earlier import can't overwrite a newer one ("latest wins").

Nothing leaves your machine (for now)Today the viewer only reads files locally. Uploading scans to a case on the server arrives with the web↔API work on Day 2. The API side already exists and is tested.

What to look at with a real scan

  • Warnings under the object: e.g. "size looks wrong for millimetres" means the file is probably in metres or microns.
  • Triangle count and import time. Report your largest file's numbers; the target is under 3 s for 1M triangles.
  • Standard views (keys 1–5). "Up" and "front" are estimated from the scan's shape. If occlusal view shows the jaw from below, or buccal shows it from the back, note the file; scanners differ in how they orient exports.
  • Colours (PLY only): toggle "colors" on the object.

Keeping a personal demo set

The demo button always uses the generated jaws. There is no setting yet to point it at your own files. Until then:

  • Keep your sets in folders under data/, e.g. data/demo/case-a/upper.stl and lower.stl, named so roles are detected. All of data/ is gitignored, so scans never get committed.
  • Drag a whole case folder's files in at once; roles sort themselves out from the names.
  • Put the 3–5 regression cases in data/golden/. That's where the planned headless runner will look for them.
Possible addition: a configurable demo setThe demo button could load files listed in a manifest (for example apps/web/public/demo/manifest.json) when one exists, and fall back to the generated jaws otherwise. One catch: anything in public/ is copied into the production build and becomes downloadable by anyone who can reach the site. So it should be enabled only in local development, or only with synthetic files. Ask if you want it.

De-identifying scans before use

Real patient data must not be used during the MVP. Check three places before copying a scan into data/:

  1. File and folder names: scanner exports often contain the patient's name or date of birth. Rename to a code like case12_lower.stl.
  2. The STL header: a binary STL starts with an 80-byte free-text header, and some scanner software writes patient or practice details into it. Check with head -c 80 file.stl | strings.
  3. PLY comments: PLY headers can contain comment … and obj_info … lines with metadata. Check with head -c 2000 file.ply | strings | grep -iE "comment|obj_info".

The app ignores both header text and comments, but they would travel with the file if it were uploaded or shared.
