AI assist

How Dentbird-style assistance (a one-click crown, edits in plain language, prescription intake) fits into the design without rewrites, and where each kind of AI is, and is not, the right tool.

In short
  • LLMs orchestrate and interpret; geometry is computed deterministically. Claude/OpenAI turn prescriptions and plain-language requests into validated commands and explain results. They never produce margin lines or crown surfaces.
  • Every design step has a Proposer behind one async job contract. Classical algorithms (now), ML models (later) and LLMs all plug into the same slot.
  • The auto-design orchestrator chains proposers and continues only while deterministic QA checks pass. When one fails, it stops for review.
  • The agent tool loop runs in the browser. The API is a thin, keyed proxy. Agent edits land as one previewed transaction the user accepts or reverts.
  • Status: contracts and the LLM proxy are Built · Day 1. Orchestrator, agent UI and Rx intake are Planned · Day 6. Trained models are Post-MVP.

What AI is (and is not) good for here

A crown has to fit the prepared tooth to about 0.05 mm. General-purpose LLMs read text and images well, but they cannot place points on a 1-million-triangle mesh at that precision, and they cannot be audited the way an algorithm can. Specialized 3D deep-learning models (what Dentbird uses) can do geometry, but they need training data we don't have yet. So each task goes to the tool that can actually do it:

The Proposer contract

Built · Day 1 as schemas in packages/shared/src/proposer.ts. A proposer suggests the output of one design step (a tooth frame, a margin line, an insertion axis, a crown). Each proposer is an async job, so a local algorithm and a remote GPU model look the same to the caller.

Identity
ProposerId = <namespace>.<name>@<version>, namespace ∈ classical | ml | llm, e.g. classical.livewire-margin@1, ml.margin-unet@0.3.1 (pattern-validated).
Inputs
Meshes as MeshRef (sha256 + units mm + frame), never face indices. Face IDs change on re-import and BVH build. A server can fetch the bytes by fileId and verify the hash.
Output
Step-specific and typed unknown in the envelope. The consumer validates it against that step's schema (e.g. MarginLine).
QA
QaCheck[] of {id, passed, value?, threshold?, message}: deterministic, numeric and explainable.
Provenance
proposerId@version on every result, plus modelHash for ML proposers, so every proposal can be traced to the code or weights that made it.

Auto-design orchestrator ("one-click crown")

Planned · Day 6 The orchestrator runs the step proposers in order and checks each result's QA before continuing. Classical proposers have no calibrated confidence, so the gate is pass/fail on measurable checks, not a "confidence threshold".

  • Proposals are overlays, not edits. The UI shows each proposal as a ghost with Accept / Edit / Reject. Accepting applies it through the normal command path, so undo works.
  • Invalidation. Changing an upstream result (e.g. moving the margin) marks downstream steps stale (downstreamSteps() in packages/shared/src/design.ts). The orchestrator re-runs only those.
  • Every proposal is logged as a ProposalEvent with what the user finally kept (see Data flywheel).

LLM agent loop

The agent lets a user say what they want ("open the distal contact a bit", "reduce occlusal height on 46 by 0.2 mm") and see the result. The loop runs in the browser, because geometry, metrics, view capture and the preview all live there. A server-side loop would need two-way tool-call messaging back to the browser. The API only holds the keys and forwards provider calls.

Tools the agent gets

Action tools are generated from the clinical command schemas (packages/shared/src/commands.ts → agentToolDefs() in tools.ts, via zod v4's z.toJSONSchema()). So the agent can do exactly what a user can do through a command, nothing more. Arguments are tooth-local and clinical (mesial, buccal, occlusal…) because LLMs are unreliable with world-space xyz. This table matches the generated output. The full JSON is in Data contracts → Generated tool definitions.

Rx intake

Planned · Day 6 The user pastes the prescription text (photo or PDF upload is a stretch goal). The browser sends it with purpose: 'rx-intake', asking for output that matches CaseSetup: teeth (FDI), restoration type, material, shade, notes. The result is validated by zod and shown as a pre-filled form; nothing is saved until the user confirms. patientRef is a pseudonymous reference (≤ 64 chars), never a name. This week, intake is tested only with synthetic prescriptions.

Data flywheel

The ML models on the roadmap need labelled examples, and the cheapest labels are the corrections users make anyway. Each time a proposal is shown, the app records a ProposalEvent with artifacts, not just counts:

  • Built · Day 1 Storage: POST /api/proposal-events validates the event and stores it in proposal_events, indexed by org + case and by step + proposer.
  • Planned · Day 6 Emitting events from the UI for every accepted, edited or rejected proposal.
  • Post-MVP Backfill of the ~100 in-house cases into the same "training bundle" format. Margin and axis come from exocad project files where present; otherwise the margin is derived from the finished crown's intaglio rim.

Safety and privacy

  • Keys stay on the server. The browser never sees API keys or chooses models. The proxy enforces auth, rate limits and the allowlist.
  • No patient identifiers to LLMs. Payloads carry case metadata, computed metrics and rendered images only. patientRef is pseudonymous.
  • Agent edits are reversible and bounded. Arguments are range-checked by zod (e.g. mm ≤ 2, deg within ±30). A batch lands as one transaction the user must accept.
  • Synthetic data only this week. Real prescriptions contain patient data.
Before any real patient dataPut a BAA or equivalent zero-retention terms in place with each LLM and cloud vendor, de-identify everything before LLM calls, and plan the medical-device regulatory path (FDA 510(k) / EU MDR). None of this is in the 1-week MVP.

ML roadmap

Post-MVP Each step below plugs into an existing Proposer slot, so the app does not change shape.

Where models runThe production VM (12 vCPU, 6 GB RAM, no GPU) hosts the web app, API and database only. Model inference runs on a separate GPU host behind the same HTTP job contract. Small models could also run on CPU via ONNX in a spare container.
Deeper detail: making the contracts cross-language

zod v4 schemas in packages/shared are the single source of truth. JSON Schema produced by z.toJSONSchema() (as on the Data contracts page) can generate pydantic models for the Python service, so ProposalInput, ProposalResult and ProposalJobStatus stay identical on both sides. Mesh inputs are MeshRefs with explicit units: 'mm' and frame, so a Python service can fetch them through the API and verify the sha256 without sharing in-memory state with the browser.
