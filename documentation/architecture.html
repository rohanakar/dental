System architecture

The parts of DentalCAD, how data moves between them, and the six principles that let AI plug in and let the backend move between clouds without rewrites.

In short
  • Thick client, thin server. Geometry runs in the browser (three.js and Web Workers). The server stores cases and scans, handles login, and proxies LLM calls.
  • One shared contract package (packages/shared, zod). It defines the design document, commands, AI tools, Proposer jobs and REST shapes for both sides.
  • Typed commands on a typed document are the only way state changes, for humans and AI alike.
  • Ports and adapters on the server: Postgres, blob storage, auth, LLMs and jobs are each swappable through env vars.
  • AI is a plug-in through the Proposer contract and command-generated tools, not a separate system.

The six principles

1 · Every mutation is a typed command on a typed document

The DesignDocument (case setup, scan references, and per-tooth frame, margin, axis, parameters, crown and step status) changes only through Commands validated by zod. The UI, keyboard shortcuts, the auto-design orchestrator and the LLM agent all use that path. Undo is a stack of immutable document snapshots with structural sharing. An agent's batch of changes is one snapshot, so a single Revert undoes it. Contracts built Command bus + snapshots · Day 4

2 · Heavy geometry runs in Web Workers

Parsing, welding, BVH building and (soon) every design algorithm run off the main thread through Comlink, with buffers transferred rather than copied. The main thread renders and handles direct manipulation (picking, gizmo, sculpt brushes on the ~30–60k-vertex crown). Built · import pipeline

3 · Meshes are content-addressed; frames and units are explicit

A MeshRef carries the sha256 of the bytes, the unit (always mm) and the coordinate frame. The same reference means the same thing in the browser, on the API, and in a future Python ML service. The upload path verifies the hash on the server. Built

4 · AI plugs in through contracts, not special cases

Each design step has Proposers: async, versioned jobs (classical.* in the browser, ml.* over HTTP later, llm.* where text or vision is enough). LLM agent tools are generated from the clinical command schemas, so the agent can only do what a user can do. Contracts built Runtime · Day 6

5 · Ports and adapters on the server

Domain code depends on interfaces (BlobStore, AuthPort, LlmProvider, JobQueue, repositories). Adapters are chosen by env var. Only open protocols are used: SQL, the S3 API, and HTTP/JSON. Built

6 · Configuration, not code, decides where it runs

One .env sets the public URL (root or sub-path), storage driver, LLM provider and model, and secrets. The same images run locally, on the OCI VM, or on managed infrastructure later. Built

Trade-offs we accepted

  • Browser does the heavy lifting. Fast interaction and a tiny server, but performance depends on the user's machine. A mid-range laptop is the target.
  • Uploads go through the API rather than presigned URLs. Storage backends stay interchangeable, at the cost of API bandwidth. Presigned multipart comes later for scale.
  • LLM responses are non-streaming for now. Simpler adapters; SSE comes later.
  • One VM, no GPU. Specialised models will run on a separate GPU host behind the same Proposer contract.

Each trade-off is recorded with alternatives in the decision log.
