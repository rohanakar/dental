3D & infra primer for web developers

You know HTTP, databases, React and Docker. This page covers what most web developers have never needed but this project depends on: triangle meshes, the GPU, spatial indexes, geometry algorithms, threads in the browser, and some less common infrastructure such as Caddy. Each idea gets an everyday analogy, then where it appears in our code.

The whole project in one sentence

DentalCAD loads a big list of triangles (the scan), builds an index so it can ask "what's under the mouse?" or "how far is this point from that surface?" quickly, draws it with the GPU, and will run a chain of geometry steps that turn the scan into a new closed set of triangles (the crown) saved as a file a milling machine can cut.

1 · Shapes as data

A 3D model is a list of triangles

Analogy: a disco ball, or a paper model made of flat triangular pieces. With small enough triangles, a surface looks smooth. A tooth scan is a surface like that, typically with 200,000 to over a million triangles.

The data is two arrays:

ArrayWhat it holdsWeb analogy
positionsEvery corner point (vertex) as x, y, z numbers: [x0,y0,z0, x1,y1,z1, …]A table of unique rows
indexEvery triangle as three vertex numbers: [0,1,2, 2,1,3, …]Foreign keys into that table

Neighbouring triangles share corners, so storing each corner once and referring to it by number saves memory and, more importantly, tells you which triangles are connected. Almost every geometry algorithm needs that connectivity. In our code this pair is the IndexedMesh type (apps/web/src/geometry/mesh.ts).

File formats: STL and PLY

  • STL is the lowest common denominator of 3D printing and milling. It's a "triangle soup": each triangle lists its three corners in full, with no sharing. A binary STL is an 80-byte header, a count, then 50 bytes per triangle, so 1M triangles is a 50 MB file. There are no colours and no units (dental files are millimetres by convention). There is also an ASCII variant, and the trap that some binary files' headers start with the word "solid", which is how ASCII files start. Our parser checks the file size to tell them apart.
  • PLY has a small text header describing its tables, then a vertex table (position, often colour) and a face table (vertex numbers). It's already indexed and can carry colour, which helps users tell gum from tooth.

Code: apps/web/src/geometry/stl.ts, ply.ts.

Welding: deduplicating corners

Analogy: normalising a denormalised database table. After parsing an STL we hash each corner's exact bit pattern; identical corners merge into one vertex and the triangles are rewritten to point at it. It must be exact: STL writers copy the same float bits for a shared corner, and "close enough" merging can glue together points that are genuinely separate (e.g. across a thin gap). One subtle case: -0.0 and +0.0 are equal numbers with different bits, so they are normalised first. A unit test covers exactly this. Code: weld.ts.

Cleanup: removing junk triangles

Scans contain debris: triangles with zero area, duplicate triangles, and small floating islands (a bit of cheek or tongue). Cleanup removes them, after welding, because you can only find "duplicate" or "disconnected" once you know which corners are shared. Code: cleanup.ts.

Units, coordinates and frames

  • Units: everything is millimetres. Clinical tolerances are about 0.05 mm (thinner than a human hair). Because STL has no units, the importer warns when a jaw is implausibly large or small (meaning the file is probably in metres or microns).
  • Coordinates: x, y, z with the right-hand rule. Each scanner picks its own "up", so the code never assumes +z is up.
  • Frames: a frame is a local set of axes. We describe the tooth in clinical directions (mesial = toward the front of the arch, buccal = toward the cheek, occlusal = toward the bite). "Move the crown 0.2 mm mesial" is converted to x/y/z through the ToothFrame. That's why the LLM tools speak clinical directions, not xyz.

Normals: which way a surface faces

A normal is a unit-length arrow sticking straight out of the surface. Analogy: a pin stuck perpendicular into a pincushion. Normals drive lighting (surfaces facing the light are brighter), offsets ("push the surface 0.04 mm outward" means move along the normal), and undercut checks (a surface facing away from the insertion direction is an undercut). A vertex normal is the average of its neighbouring triangles' normals, weighted by triangle area so tiny slivers don't skew it. Code: normals.ts.

PCA: finding a shape's main directions

Analogy: lay a handful of rice on a table and ask which way it's spread most, which way least. For a dental arch, the direction of least spread is roughly "up" (the arch is flat-ish), and the longest is side to side. PCA (principal component analysis) computes those directions from the 3×3 covariance of all vertices. We use it to guess the default view directions before the user has set up a tooth. Code: pca.ts, apps/web/src/engine/viewFrame.ts.

2 · Drawing them: the GPU, three.js and cameras

The GPU draws triangles, very fast

The graphics card is a specialised processor that colours millions of triangles in parallel. In the browser you talk to it through WebGL, a low-level API where you upload arrays of numbers (buffers) and tiny programs (shaders) that run once per vertex and once per pixel. Raw WebGL is verbose, roughly like writing your own HTTP stack on sockets.

three.js is the popular library that wraps it. Its vocabulary:

three.js conceptPlain meaningIn our code
BufferGeometryThe positions/index/normals/colours arrays, ready for the GPUbuilt from IndexedMesh
MaterialHow a surface is coloured (the shader + its settings)engine/materials.ts
MeshGeometry + material = one drawable objectone per scan
SceneThe tree of everything to draw (like the DOM, for 3D)inside Viewer
CameraWhere we look from, and the lensperspective or orthographic
WebGLRendererTurns scene + camera into pixels on a <canvas>engine/Viewer.ts
Why not React for 3D?There is a React wrapper (react-three-fiber), but we keep the 3D engine as a plain class (Viewer) and let React only draw panels and buttons. 3D rendering is a loop over big arrays, and we want full control over exactly when it redraws and how buffers update. React's re-render model gets in the way. React tells the engine what to do through a small API in state/sceneController.ts.

Render loop vs render on demand

Games redraw 60 times a second whether or not anything changed. A CAD viewer is mostly still, so we render on demand: only when the camera moves or the scene changes. That saves battery and leaves the GPU free for heavy work.

Cameras: perspective vs orthographic

  • Perspective: like your eye or a phone camera; far things look smaller.
  • Orthographic: like an architect's drawing; size doesn't change with distance, which makes distances easier to judge. Technicians switch to it for checking (key O).

Orbiting (dragging to rotate the view) normally spins around the centre of the scene. Dental technicians zoom into one tooth, so we orbit around the surface point under the cursor: on mouse-down we shoot a ray into the scene (see part 3), and the hit becomes the pivot. Navigation comes from the camera-controls library.

Shading with matcaps

Realistic lighting needs light sources, shadows and tuning, and dental surfaces can still look flat. A matcap ("material capture") is a small picture of a lit sphere. For each pixel, the shader takes the surface's facing direction (its normal, relative to the camera) and looks up the colour at the matching spot on the sphere picture. Analogy: painting by numbers, where the number is "which way am I facing". It's cheap, looks the same from every angle, and shows every bump clearly. We draw the sphere pictures in code at startup (engine/matcap.ts), so there are no image files.

Back faces, colours and transparency

  • Back faces: each triangle has a front and a back, decided by the order of its corners ("winding"). Scans are open surfaces, so you can see their insides. We tint back faces differently so holes and inside-out regions are obvious (a shader check of gl_FrontFacing).
  • Colour spaces: colours in files are "sRGB" (gamma-encoded for screens) while lighting maths wants "linear" values. Mixing them up makes colours washed out or too dark, so PLY colours are converted on load.
  • Transparency is hard: the GPU uses a depth buffer (per pixel, "how close is the nearest thing drawn so far") to hide what's behind. See-through objects break that, because what's behind must be drawn first. We draw opaque objects first, then transparent ones back faces first, then front faces. It isn't perfect, but it's good enough for "see the prep through the crown".

3 · Asking questions of shapes: raycasting and the BVH

Almost every interaction is a geometric question: which triangle is under the mouse? (picking), how far is this crown point from the opposing tooth? (occlusion colour map), what's the first surface along this direction? (undercut blockout).

A raycast fires an imaginary laser from a point in a direction and reports the first triangle it hits. Done naively, that means testing all one million triangles, for every mouse move.

A BVH (bounding volume hierarchy) is a spatial index. Analogy: a B-tree index for 3D, or finding a book by floor, then shelf, then row, instead of scanning every book. It groups triangles into boxes, boxes into bigger boxes, and so on. A ray only descends into boxes it actually passes through, about 20 levels for a million triangles, so each query touches a few hundred triangles instead of a million.

The gotcha we designed aroundThe BVH library (three-mesh-bvh) reorders the triangle list while building, so triangle number 5,000 before is a different triangle after. Anything that stored triangle numbers earlier is now silently wrong. So we build the BVH once in the worker, ship it to the main thread (MeshBVH.serialize/deserialize), treat that order as the only one, and store margin points as 3D coordinates, never as triangle numbers.

4 · Changing shapes: the geometry behind a crown

Most of this is Planned · Days 2–5. Here are the ideas in plain terms; the maths is on the Geometry pipeline page.

ConceptPlain-language ideaUsed for
CurvatureHow sharply the surface bends at a point, and whether it bulges out (convex, a ridge) or dips in (concave, a groove). Like reading the slope on a contour map.The margin follows the prep's convex edge and must not slip into the groove beside it.
Shortest paths on a meshTreat vertices as cities and edges as roads, then run Dijkstra, the same algorithm as map routing. Make roads along ridges "cheap" and the route hugs the ridge.Live-wire margin tool: click a few points; the path between them snaps to the edge live as you move the mouse.

Why "exact" matters hereA float32 number has about 7 significant digits. At jaw scale (around 100 mm) that's a resolution of about 0.00001 mm, thousands of times finer than the 0.05 mm clinical tolerance. So float32 is fine for storage, but algorithms must avoid accumulating error (e.g. repeated smoothing that slowly shrinks a shape).

5 · Keeping the browser fast

The 16-millisecond budget

For smooth motion the screen updates 60 times a second, so each frame has about 16 ms. JavaScript on the main thread shares that time with layout, React and input handling. Parsing a 50 MB scan takes far longer than 16 ms, and on the main thread the page would freeze.

Web Workers: background threads for the browser

A Web Worker runs JavaScript on another CPU core. It has its own memory and can't touch the page; you exchange messages. Comlink makes that look like calling an async function (await worker.importScan(bytes)), much like an RPC client.

Messages are normally copied, and copying 50 MB twice is slow. Transferables move a buffer to the other thread instead (the sender loses access). Analogy: handing someone a box instead of photocopying its contents. Every big array we send is transferred.

Comlink can't cancel a call already running. If you drop a new file while the previous one is still processing, we use a "latest wins" counter: when the old result arrives, it's thrown away.

Typed arrays, not objects

A million vertices as {x, y, z} objects would use several times more memory and give the garbage collector a lot to do. Instead we use typed arrays (Float32Array, Uint32Array): one compact block of raw numbers, exactly what the GPU wants and transferable between threads. A welded 1M-triangle scan is roughly 500k vertices, about 6 MB of positions, 6 MB of normals and 12 MB of index.

6 · Infrastructure you may not have met

Caddy, explained

Caddy is a web server and reverse proxy, in the same family as nginx and Apache, written in Go. It's known for two things: a short, readable config file (the Caddyfile) and automatic HTTPS (it obtains and renews Let's Encrypt certificates by itself when given a domain name).

Analogy: a receptionist at the front door. Visitors (browser requests) arrive. Requests for brochures (the app's HTML/JS/CSS files) are handed out from the shelf. Requests for a specific person (/api/…) are walked to the right office (the API container). The visitor never sees the building's internal layout.

How to read a Caddyfile (two-minute version)

{                       # global options block
    admin off
}

:80 {                   # a "site block": which address to serve (plain HTTP on port 80)
    encode zstd gzip    # a "directive": do this for every request in the block

    handle /api/* {     # "handle" blocks are mutually exclusive; the most specific path wins
        reverse_proxy api:3000
    }
    handle {            # fallback for everything else
        root * /srv
        try_files {path} /index.html
        file_server
    }
}

For comparison, the nginx equivalent of the important part:

location /api/ { proxy_pass http://api:3000; proxy_request_buffering off; }
location /     { root /srv; try_files $uri /index.html; }

Why both Nginx Proxy Manager and Caddy?

  • The app's routing rules travel with the app. SPA fallback, /api routing, cache headers, upload streaming and sub-path stripping live in the repo's Caddyfile, versioned with the code. Nginx Proxy Manager doesn't need to know any of it.
  • Portability. Any HTTPS front (NPM, a cloud load balancer) only has to forward to Caddy; nothing app-specific moves with it.
  • The cost is one small extra hop, which is negligible.

Files: infra/Caddyfile, infra/proxy.Dockerfile (builds the web app, then copies the output into a Caddy image). See Deployment for operating it.

Docker Compose details that matter here

  • Service names are hostnames. Inside the Compose network, the API reaches Postgres at db:5432 and Caddy reaches the API at api:3000. Nothing is published on the host: Caddy also joins the external network shared_net, where Nginx Proxy Manager reaches it as dcad-proxy.
  • Named volumes hold state. pgdata (database) and blobs (scan files) survive container rebuilds. Deleting them deletes data.
  • Health checks make start-up ordered: the API waits until Postgres answers.
  • Memory limits (mem_limit) keep one service from starving the 6 GB VM.

arm64 vs x86

CPUs speak different instruction sets. The OCI VM (Ampere) and Apple-silicon Macs are arm64 (also called aarch64); most cloud servers and older PCs are x86-64 (amd64). A Docker image is built for one of them. Our base images (Node, Postgres, Caddy) publish both, and we build on the VM itself, so everything is native arm64. The trap: an image built on an Intel laptop and copied over would fail on the VM, or run very slowly under emulation.

Content addressing and integrity

Every scan is identified by the sha256 hash of its bytes, its fingerprint. Two identical files have the same id wherever they are (browser, API, a future ML service), and a single flipped bit changes it. On upload (built in the API; the web app starts uploading on Day 2), the browser gzips the file and sends the hash of the original. The API streams the compressed bytes to storage while decompressing a copy just to compute the hash, and rejects the upload (and deletes what it stored) on a mismatch. The whole file is never held in memory: measured, a 150 MB upload kept the API at about 112 MiB.

Optimistic concurrency

Two tabs editing the same case could overwrite each other. Each save says "I'm based on version 7". If the server is already at version 8, it answers 409 Conflict instead of silently overwriting. Analogy: a wiki's "someone edited this page while you were editing". There are no locks, so nobody waits.

Multi-tenancy with organisations

Each user belongs to an organisation (a lab); a personal one is created at sign-up. Every database query includes the organisation id, so one lab can never read another's cases, and asking for someone else's case returns 404, not 403, to avoid revealing that it exists. Auth is handled by the Better Auth library, with session cookies, and its tables live in our own Postgres.

7 · AI plumbing

LLM tool calling

Besides text, modern LLM APIs can answer with a tool call: a structured request like {"name": "move_crown", "input": {"fdi": 36, "direction": "mesial", "mm": 0.2}}. You send the model a list of tools, each described by a JSON Schema. When it "calls" one, your code runs it and sends the result back, and the model continues. It's an RPC protocol where the model is the client.

In DentalCAD, the tools are generated from the same zod schemas that validate user commands (agentToolDefs() in packages/shared/src/tools.ts). So the model can only request things a user could do, every request is validated, and each batch is shown with Accept/Revert. The model never produces geometry itself. Contracts built Agent loop · Day 6

zod as the single source of truth

zod defines a data shape once in TypeScript and gives you three things: static types, runtime validation (parse untrusted input and get a clear error if it's wrong), and JSON Schema (for the LLM tools and the reference docs). Both the web app and the API import the same definitions from packages/shared, so a change breaks typechecking everywhere it matters.

8 · How we test this kind of code

Geometry code is unusual to test: outputs are huge arrays, and "correct" is often a property ("closed", "nothing thinner than 0.5 mm") rather than an exact value. In short:

  • Tiny hand-made inputs: a cube written as an STL must weld to exactly 8 corners and 12 triangles.
  • Round trips: write a PLY, read it back, get the same data; serialize the BVH in the worker, rebuild it on the main thread, and the same ray hits the same triangle.
  • Synthetic data: the generated demo jaw (with a prep on tooth 36) is used in tests, never patient data.
  • Contract tests: one test suite run against two storage back-ends (local disk and S3), which proves they're swappable.
  • Real infrastructure for integration: API tests run against real Postgres and S3-compatible storage in Docker, not mocks.
  • Performance as a test: a 1M-triangle import must finish within a budget.

Where to start reading the code

A suggested path for a developer new to 3D, from most familiar to least:

  1. packages/shared/src/design.ts and commands.ts: the data model, plain TypeScript + zod.
  2. apps/api/src/http/app.ts → domain/files.ts: a familiar web backend; then the upload streaming.
  3. apps/web/src/ui/ScanImport.tsx → state/sceneController.ts: React to engine boundary.
  4. apps/web/src/workers/geometry.worker.ts → geometry/processScan.ts: the import pipeline, one function per step.
  5. geometry/stl.ts, weld.ts, cleanup.ts, normals.ts: small, tested, array-based algorithms. Read them alongside their *.test.ts.
  6. apps/web/src/engine/Viewer.ts: three.js scene, camera, picking, transparency.
  7. geometry/synthetic.ts: how a fake jaw is built from formulas; good for building intuition.

Then: System architecture for how it fits together, and Geometry pipeline for what's coming.
